# Existing Tools for a Single-Port Agent Artifact Gallery + Optional Obsidian Reader

Research date: 2026-09-15. Repository stats (stars, last push, license, archived flag) were pulled from the GitHub REST API on that date via `gh api repos/<owner>/<repo>`; all other claims are cited to first-party docs/READMEs. File-watching, license, and roadmap statements can go stale — re-check before committing to a tool.

## Summary

- No surveyed tool does the whole job. The closest single-binary fits for "one port, many folders, auth, mobile UI" are **Caddy `file_server` + path matchers** (multi-root and auth, no gallery UX), **FileBrowser Quantum** (multi-source file browser with indexed search, but folder-centric, not artifact/recency-oriented), and **SFTPGo** (multi-root "virtual folders", rich auth, but transfer/admin-oriented). See [§1](#1-multi-folder-static-servers-on-one-port).
- No mature "AI-agent artifact gallery" exists. Claude Code viewers index session logs, not generated artifacts; MCP artifact servers are 0–2 star MVPs. Nothing groups artifacts by project with tags, pinning, versions, or a phone-first index. See [§2](#2-ai-agent-artifact-viewers).
- The user's existing remotely-managed Cloudflare Tunnel supports **one tunnel with many public hostnames**, each mapped to a different `http://localhost:<port>` ([Cloudflare routing docs](https://developers.cloudflare.com/tunnel/concepts/routing/)). Path routing exists but is not needed: point one hostname at one new server port. Cloudflare Access is **free for up to 50 users** ([Cloudflare Access product page](https://www.cloudflare.com/sase/products/access)) and does not require an app change. See [§4](#4-cloudflare-tunnel--access-facts).
- For Obsidian, **Quartz v5** is the best embeddable read-only renderer for this stack: full Obsidian-flavored Markdown (wikilinks, callouts, backlinks, tags, graph, full-text search), static output that can be served from the single server under `/vault`, with auth supplied by the outer layer ([Quartz feature list](https://quartz.jzhao.xyz/features/)). Perlite is the zero-build alternative if PHP is available ([Perlite README](https://github.com/secure-77/Perlite)). See [§3](#3-markdownobsidian-rendering).
- Recommended shape: **build a thin purpose-built gallery/coordinator** (Python or Node) that owns one port, watches configured artifact roots, builds a mobile card index (project grouping, recency, frontmatter tags, search, pin), and reverse-proxies or statically mounts Quartz for the vault — reusing Caddy/Quartz/watchfiles rather than adopting any single existing server wholesale. See [Recommendations](#recommendations).

Additional findings:

- FileBrowser Quantum's own comparison chart positions it against Filestash/Nextcloud/FileRun and marks "Multiple sources at once" as ✅ for Quantum and ❌ for the original FileBrowser ([README comparison chart](https://github.com/gtsteffaniak/filebrowser)).

- miniserve already ships the QR-code-to-phone affordance the user wants ([README](https://github.com/svenstaro/miniserve)), but only for a single root.

## 4. Cloudflare Tunnel + Access facts

Sources: Cloudflare Tunnel ["Routing"](https://developers.cloudflare.com/tunnel/concepts/routing/), ["Create a tunnel (dashboard)"](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/get-started/create-remote-tunnel/), ["Configuration file" (locally-managed)](https://developers.cloudflare.com/tunnel/features/locally-managed-tunnels/configuration-file/), ["Origin parameters"](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/origin-parameters/), ["Publish a self-hosted application"](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/), ["Policies"](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/), ["Seat management"](https://developers.cloudflare.com/cloudflare-one/team-and-resources/users/seat-management/), ["Account limits"](https://developers.cloudflare.com/cloudflare-one/account-limits/), ["One-time PIN"](https://developers.cloudflare.com/cloudflare-one/integrations/identity-providers/one-time-pin/), [Cloudflare Access pricing](https://www.cloudflare.com/sase/products/access).

**One tunnel, many hostnames.** Yes. "You can publish multiple applications on a single tunnel"; each published application is a public-hostname → local-service mapping such as `app.example.com` → `http://localhost:8080`, and the dashboard creates a DNS record per hostname pointing at `<UUID>.cfargotunnel.com` ([routing](https://developers.cloudflare.com/tunnel/concepts/routing/)). A tunnel can therefore serve `gallery.example.com → localhost:8787` and `vault.example.com → localhost:8788` simultaneously; the endpoint count ceiling is 1,000 hostname routes + tunnels per account ([account limits](https://developers.cloudflare.com/cloudflare-one/account-limits/)).

**Path routing.** In the dashboard (remotely-managed) route UI you can "specify any subdomain or path information"; path routes match but **do not strip or rewrite** — the origin receives the full path, and rewrites require edge URL Rewrite Rules or a local reverse proxy ([create a tunnel](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/get-started/create-remote-tunnel/)). For *locally-managed* tunnels the semantics are explicit: ingress rules are evaluated top-to-bottom, rules may match hostname, path, or both, a missing hostname matches all hostnames, a missing path matches all paths, the last rule must be a catch-all, and `path` may be a Go-syntax regular expression ([configuration file](https://developers.cloudflare.com/tunnel/features/locally-managed-tunnels/configuration-file/)). **Uncertainty:** the docs do not document regex support or explicit catch-all requirements for *dashboard-managed* path routes the way they do for local config files; assume prefix semantics without rewrite, and confirm ordering behavior in the dashboard before relying on it. For this project, path routing is unnecessary: use one hostname → one port.

**Access on a tunnel hostname.** Create a self-hosted Access application for the public hostname, attach policies, choose IdPs and session duration, and optionally enable `Protect with Access` on the tunnel so `cloudflared` validates the Access JWT before proxying to the origin ([self-hosted app](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/), [origin parameters](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/origin-parameters/)). Policies combine one action (Allow/Block/Bypass/Service Auth) with Include/Require/Exclude rule types and selectors such as Emails, Emails ending in, IP ranges, Country, Login Methods, and Service Token; Bypass/Service Auth evaluate before Block/Allow, then Block/Allow top-to-bottom ([policies](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/)). Access app URLs can be scoped to paths and wildcards within a hostname ([self-hosted app](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/)).

**Free-tier reality.** Access is free "for teams under 50 users" with a "50 user limit" row in the comparison table ([Access pricing](https://www.cloudflare.com/sase/products/access)); you do **not** need a paid plan to publish an app via Tunnel, and seats are only consumed when you use Access policies ([routing note](https://developers.cloudflare.com/tunnel/concepts/routing/)). A seat is consumed by an authentication event and held until the user is removed ([seat management](https://developers.cloudflare.com/cloudflare-one/team-and-resources/users/seat-management/)); service tokens do not consume seats ([seat management](https://developers.cloudflare.com/cloudflare-one/team-and-resources/users/seat-management/)). For a single user, one seat is used. Login methods: OTP is configured per account, and new Zero Trust orgs default to the Cloudflare IdP rather than auto-adding OTP ([one-time PIN](https://developers.cloudflare.com/cloudflare-one/integrations/identity-providers/one-time-pin/)); Google/Microsoft/other IdPs are configured under Zero Trust → Integrations → Identity providers ([IdP docs](https://developers.cloudflare.com/cloudflare-one/integrations/identity-providers/)). Limits that could matter: 500 Access applications, 50 identity providers, 50 service tokens, 1,000 rules per application ([account limits](https://developers.cloudflare.com/cloudflare-one/account-limits/)). Config lives in the Cloudflare dashboard/API ("where the app/Access config lives": Zero Trust → Access controls → Applications for apps/policies; Networking → Tunnels → Routes for tunnel routes) and can be managed via API/Terraform ([self-hosted app](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/), [policies](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/)).

**Practical implication for this utility:** keep the existing remotely-managed tunnel, add one published-application route for one hostname → `http://localhost:<gallery-port>`, and put an Access self-hosted app + email-allow policy on that hostname. No tunnel reinstall, no new cloudflared process, no extra port.

## 5. Remote-access alternatives with identity

- **Tailscale Serve**: `tailscale serve` exposes a local service "securely within your tailnet" with automatic HTTPS certs, supports reverse proxy to a local port and file/dir serving; only devices in the tailnet (with your ACLs) can reach it ([Tailscale Serve KB](https://tailscale.com/kb/1242/tailscale-serve)). Better than Cloudflare Access when both phone and server are on the tailnet and you want zero-login access per device; weaker if you need browser login from arbitrary devices.
- **Tailscale Funnel**: public internet exposure of a local service, beta, limited to ports 443/8443/10000, TLS-only, with non-configurable bandwidth limits — public means no identity gate of its own ([Tailscale Funnel KB](https://tailscale.com/kb/1223/funnel)).
- **ngrok**: free plan has 1 dev domain, up to 3 online endpoints, 1 GB/month and 20k requests/month, and shows an interstitial on HTML traffic; OAuth/OIDC "traffic identities" are metered at 3 MAU/month on free ([ngrok free plan limits](https://ngrok.com/docs/pricing-limits/free-plan-limits/)). Meaningfully better for quick throwaway shares; worse for an always-on personal gallery (quotas/interstitial).
- **zrok**: open-source, zero-trust sharing built on OpenZiti; `zrok share public` is open to anyone, while `zrok share private` is restricted to other zrok users (identity-based) ([zrok README](https://raw.githubusercontent.com/openziti/zrok/main/README.md)). Better if you want self-hostable identity-based sharing; adds an account/environment to the phone side.

None of these beat the existing Cloudflare Tunnel + Access combination for "personal phone access with login" given the tunnel is already installed and Access is free at this scale.

## 6. Auth for self-hosted tools (single user)

- **Cloudflare Access (recommended outer layer for this project)**: free ≤50 users, email OTP or IdP login, service tokens for machines, no app code change, JWT validation available inside `cloudflared` ([pricing](https://www.cloudflare.com/sase/products/access), [policies](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/), [origin parameters](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/origin-parameters/)). One seat consumed by the single human user; service tokens free of seats ([seat management](https://developers.cloudflare.com/cloudflare-one/team-and-resources/users/seat-management/)).
- **App-level auth shipped by tools**: FileBrowser Quantum (OIDC/LDAP/JWT/password+2FA/proxy) ([README](https://github.com/gtsteffaniak/filebrowser)); dufs (`-a user:pass@/path:rw`) ([README](https://github.com/sigoden/dufs)); miniserve (`--auth`, hashed, `--auth-file`) ([README](https://github.com/svenstaro/miniserve)); static-web-server (Basic/BCrypt) ([README](https://github.com/static-web-server/static-web-server)); http-server (`--user`/`--password`) ([README](https://raw.githubusercontent.com/http-party/http-server/master/README.md)); Caddy (`basic_auth`, path-scoped) ([docs](https://caddyserver.com/docs/caddyfile/directives/basic_auth)); nginx (`auth_basic`) ([docs](http://nginx.org/en/docs/http/ngx_http_auth_basic_module.html)); SFTPGo (users/OIDC/2FA) ([docs](https://docs.sftpgo.com/latest/web-interfaces/)). gossa deliberately ships no auth and delegates to a proxy ([README](https://raw.githubusercontent.com/pldubouilh/gossa/master/readme.md)); vercel/serve documents no auth ([README](https://raw.githubusercontent.com/vercel/serve/main/readme.md)).
- **Authelia / Authentik**: full SSO/MFA portals that sit in front of many apps via forward-auth (Authelia: "Single Sign-On Multi-Factor portal for web apps" ([repo](https://github.com/authelia/authelia)); Authentik: "the authentication glue you need" ([repo](https://github.com/goauthentik/authentik))). Both are more moving parts (datastore/Redis, config, a reverse proxy) than one user needs; adopt only if you want the same login across several self-hosted apps.
- For a single user, **Cloudflare Access wins** (zero app integration, free, phone-friendly OTP/IdP), with app-level auth as defense-in-depth only if the server is also reachable on the LAN/untrusted networks.

## 7. Watch-folder → index generation

Pick **watchfiles** for a Python implementation and **chokidar** for a Node implementation; both are mature first-party-documented watchers. `watchfiles` provides `watch()`/`awatch()` generators and `run_process`/`arun_process`, uses the Rust `notify` crate for OS-level notifications, and supports Python 3.10–3.15 (fine for the user's 3.14) ([watchfiles README](https://raw.githubusercontent.com/samuelcolvin/watchfiles/main/README.md)). `chokidar` normalizes `fs.watch` events, supports atomic writes and `awaitWriteFinish` (important because agents often write files in chunks or via rename), recursive watching, and is on v5 (ESM-only, Node 20+) as of Nov 2025 ([chokidar README](https://raw.githubusercontent.com/paulmillr/chokidar/main/README.md)). Either way, debounce bursts, ignore `.git`/`node_modules`, and plan for inotify watch limits on Linux (`fs.inotify.max_user_watches`) ([chokidar troubleshooting](https://raw.githubusercontent.com/paulmillr/chokidar/main/README.md)).

## 8. Enhancement opportunities (gaps a purpose-built tool could fill)

1. **Artifact-first index, not folder-first.** Every surveyed server shows a directory tree. Nothing shows "what did my agents publish lately", grouped by project, sorted by recency, with a card per lesson/explanation. This is the single biggest gap ([§1](#1-multi-folder-static-servers-on-one-port), [§2](#2-ai-agent-artifact-viewers)).
2. **Publish primitive for agents.** No tool here gives agents a one-command "publish this HTML/Markdown and return a stable URL" contract; the closest is occ-artifact-gallery's registry/CLI MVP and SFTPGo share links ([occ-artifact-gallery](https://raw.githubusercontent.com/shadoprizm/occ-artifact-gallery/main/README.md), [SFTPGo](https://docs.sftpgo.com/latest/web-interfaces/)). A local `publish` CLI (curl to `localhost`) that copies/registers an artifact under a project/timestamp avoids per-agent servers entirely.
3. **Metadata users actually care about:** tags from frontmatter or filename, pinned items, versions on republish, project grouping, full-text search. Quartz has tags/backlinks/search for the vault ([Quartz](https://quartz.jzhao.xyz/features/)); FileBrowser Quantum has real-time indexed search and starred files ([README](https://github.com/gtsteffaniak/filebrowser)); no artifact gallery combines these.
4. **Phone-first affordances**: QR code to open the current artifact (miniserve already proves this feature, [README](https://github.com/svenstaro/miniserve)), PWA install (Claude Code Viewer does this for sessions, [README](https://raw.githubusercontent.com/d-kimuson/claude-code-viewer/main/README.md)), and a thumb-friendly index.
5. **One server, one port, one hostname.** Today's pattern is N `http.server` processes + N tunnel routes. The tunnel supports one hostname → one port, so a coordinator that fans out to artifact roots (and optionally to Quartz's static output) removes the collision class entirely ([Cloudflare routing](https://developers.cloudflare.com/tunnel/concepts/routing/)).
6. **Auth done once.** Put Access on the single hostname instead of per-artifact protections; optionally validate the JWT in the app for defense-in-depth ([origin parameters](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/origin-parameters/)).
7. **Obsidian is worth serving only read-only and selectively.** Quartz can publish the whole vault read-only with search/backlinks as a `/vault` path prefix; if you only want a few notes, obsidian-export/private-page filters keep the rest out ([Quartz private pages](https://quartz.jzhao.xyz/features/private-pages), [obsidian-export](https://raw.githubusercontent.com/zoni/obsidian-export/main/README.md)). Treat the vault as a second "root" in the gallery rather than a separate publish pipeline.

## Recommendations

**Reuse**

- **Tunnel/Access**: keep the existing remotely-managed cloudflared service; add one published-application route (one hostname → one local port) and one Access self-hosted app with an email allow policy. Free and no app changes ([routing](https://developers.cloudflare.com/tunnel/concepts/routing/), [pricing](https://www.cloudflare.com/sase/products/access)).
- **Static serving substrate**: Caddy `file_server` + `handle_path` if you want an off-the-shelf multi-root server with basic auth and JSON listings ([file_server](https://caddyserver.com/docs/caddyfile/directives/file_server), [basic_auth](https://caddyserver.com/docs/caddyfile/directives/basic_auth)); otherwise serve directly from the new coordinator (Node/Python) and skip Caddy.
- **Obsidian**: Quartz v5 as a build target under `/vault`, rebuilt on vault changes via watchfiles/chokidar ([Quartz](https://quartz.jzhao.xyz/features/)).
- **Reference implementations to borrow from, not adopt wholesale**: miniserve's QR code, FileBrowser Quantum's multi-source config + indexed search, Claude Code Viewer's `--base-path`/PWA pattern, occ-artifact-gallery's registry/allowlist/response-contract idea ([miniserve](https://github.com/svenstaro/miniserve), [FileBrowser Quantum](https://github.com/gtsteffaniak/filebrowser), [claude-code-viewer](https://raw.githubusercontent.com/d-kimuson/claude-code-viewer/main/README.md), [occ-artifact-gallery](https://raw.githubusercontent.com/shadoprizm/occ-artifact-gallery/main/README.md)).

**Build**

- A small single-port coordinator with: a config file listing artifact roots (project → folder), a filesystem watcher (watchfiles for Python, chokidar for Node), a metadata index (frontmatter/filename tags, recency, pin state, version history on republish), a mobile card UI grouped by project, search, QR display for a selected artifact, and a `publish` command/endpoint that copies an artifact into the store and returns a URL. Reuse Quartz's output under `/vault`. Do not build a general file manager (that is the year of work FileBrowser Quantum already did).

**Risks / unknowns**

- **Archived upstream**: `filebrowser/filebrowser` is archived; only the Quantum fork is active, and it is a fast-moving fork ([repo](https://github.com/filebrowser/filebrowser), [fork README](https://github.com/gtsteffaniak/filebrowser)).
- **Path-prefix fragility**: many generated artifacts (SPAs, absolute asset paths, service workers) break under subpath hosting; relative links or per-artifact subdomains/paths need testing. Cloudflare's dashboard path routing does not strip prefixes ([create a tunnel](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/get-started/create-remote-tunnel/)), so any stripping must happen locally.
- **Remotely-managed path-route semantics**: regex paths, ordering, and catch-all behavior are documented for locally-managed config files, not clearly for dashboard routes — treat as unverified ([configuration file](https://developers.cloudflare.com/tunnel/features/locally-managed-tunnels/configuration-file/)).
- **Free-plan changes**: the 50-user Access free tier and OTP defaults are documented today but are policy, not contract; seat/auth behavior can change ([pricing](https://www.cloudflare.com/sase/products/access), [one-time PIN](https://developers.cloudflare.com/cloudflare-one/integrations/identity-providers/one-time-pin/)).
- **License/ops**: SFTPGo is AGPL with a proprietary UI theme restriction, Flowershow is AGPL, mdBook MPL-2.0; the other recommendations are permissive ([SFTPGo](https://github.com/drakkan/sftpgo), [Flowershow](https://github.com/flowershow/flowershow), [mdBook](https://github.com/rust-lang/mdBook)).
- **Watcher limits and durability**: Linux inotify limits, agents using atomic writes/renames, and tunnel drops during long uploads are operational failure modes to handle; chokidar documents the write-completion/ENOSPC issues, and Cloudflare notes DNS records survive a stopped tunnel but return 1016 errors ([chokidar](https://raw.githubusercontent.com/paulmillr/chokidar/main/README.md), [routing](https://developers.cloudflare.com/tunnel/concepts/routing/)).
- **Vault privacy**: a read-only web render of a vault is a disclosure surface; Quartz private/encrypted-page plugins help but are client-side filters, so prefer allowlisting what enters the build (obsidian-export tag filters, Quartz private-pages) over assuming everything is safe to publish ([Quartz private pages](https://quartz.jzhao.xyz/features/private-pages), [obsidian-export](https://raw.githubusercontent.com/zoni/obsidian-export/main/README.md)).
